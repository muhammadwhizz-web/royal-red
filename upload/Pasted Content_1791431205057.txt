0. Non-negotiable design law for this entire round
Before any objective, read these and follow them for the rest of Royal Red's life:

UI law:

No emojis anywhere. Not in the UI, not in boot sequences, not in receipts, not in agent messages, not in tool outputs. Emojis look childish and undercut the "majestic royal OS" feeling.

Icons must be real SVGs — vector, hand-drawn or from a licensed icon set (Lucide, Phosphor, Heroicons — pick one and stick to it). No emoji glyphs, no unicode symbols, no font icons that can fail to load.

The visual language is: majestic royal red, premium materials, fabrics and texture, crown motifs used sparingly, hacking-terminal fonts for data and code.

The crown is the signature mark. One crown, used deliberately. Not five crowns, not crown wallpaper. When a user sees the crown, it means "verified" or "sealed" or "the sovereign did this."

Color law:

Primary palette: deep royal red (#7f1d1d to #b91c1c range for dark mode, #991b1b to #dc2626 for light mode accents), rich burgundy for surfaces, deep crimson for primary actions.

Accent palette: gold/bronze (#a16207 to #eab308) used only for the crown and sealed/verified marks. Not used for anything else.

Neutral palette: near-black (#0a0606) for the deepest background, warm off-white (#faf5f0) for light mode backgrounds. No pure white, no pure black. Everything is warm-tinted.

Premium materials: subtle gradients that feel like velvet or leather, fine noise texture on surfaces (very subtle — 2–3% opacity), soft inner shadows on cards that feel embossed, gold foil effect only on the crown and verified seals.

Fabric hints: a subtle woven or damask pattern can appear on header/footer/boot backgrounds at very low opacity. Never obtrusive. Never over content.

Typography law:

Display font (headings, crown wordmark, boot sequence): a majestic serif with high contrast — try Cormorant Garamond, Playfair Display, or EB Garamond. Royal, editorial, feels engraved.

UI font (body, panels, buttons): a refined sans — try Inter, Geist, or Söhne. Neutral, modern.

Data/code font (all numbers, code blocks, event logs, tool outputs, receipt values): a hacking-terminal mono — try JetBrains Mono, IBM Plex Mono, or Berkeley Mono. This is what makes Royal Red feel like a real OS: the data layer is monospaced and feels like terminal output.

Font loading: self-host every font. Never load from Google Fonts at runtime (privacy + reliability). Subset the fonts. Preload the display font.

Component law:

Buttons: physical press feedback (translate-y + shadow change). No flat buttons.

Cards: subtle inner shadow, 1px hairline border in gold at 12% opacity, 16px corner radius.

Modals: aurora backdrop blur, crown watermark at 3% opacity behind content.

Every interactive element: keyboard-navigable, focus ring in gold, aria-* correct.

Reference points: Linear, Arc browser, Raycast, Vercel dashboard, Apple's Pro Apps, and the boot sequences from classic UNIX systems. Not Figma, not Notion, not Slack.

2. The memory system — real, persistent, cross-session
Royal Red needs a memory system that persists across sessions, across projects, across sub-agents. Not just session history. Real memory.

2.1 The memory store. New schema: RoyalRedMemory. Fields: id, scope (global / project / session / agent), key, value, source (user / agent / inferred), confidence, createdAt, updatedAt, expiresAt (nullable), tags.

2.2 The write path. When a user says "remember X," the kernel writes to RoyalRedMemory at the appropriate scope. When the agent infers something worth remembering (a user preference, a project convention), it proposes the memory and the user approves.

2.3 The read path. Before every turn, the kernel loads all memories in scope and injects them into the agent's context — but only the relevant ones. Relevance by tag match + recency + confidence. Cap the injected memory at a token budget.

2.4 The UI. A new panel: MEMORY. Shows all memories by scope. User can view, edit, delete, promote (session → project → global), demote, tag, expire. Search. Filter. Export as JSON.

2.5 The API. GET /api/royal-red/memory?scope=... — list. POST — write. PATCH /:id — update. DELETE /:id — delete. All audit-logged.

2.6 The privacy rule. Memories never leave the machine unless the user exports them. No cloud sync in this round. If cloud sync is added later, it must be end-to-end encrypted and opt-in.

Acceptance: user types "remember that I prefer royal red in dark mode." Restart the console. Ask "what theme do I prefer?" — Royal Red answers correctly. The memory appears in the MEMORY panel with scope global, source user.

7. PDF, poster, and document generation — the visual best, no overlap, no em dashes
The user asked for PDFs, posters, and documents that are visually impeccable.

7.1 PDFs. The hand-rolled PDF engine already exists. Extend it:

Real typography: embedded fonts (subset), proper kerning, real hyphenation

Multi-page with running headers/footers, page numbers

Tables with proper column widths, right-aligned numbers

Charts (bar, line, pie) rendered as vector, not raster

Images placed with correct DPI, no upscaling

No overlap, ever — the layout engine computes bounding boxes and refuses to place two elements in the same space. If the content doesn't fit, it flows to the next page.

7.2 Posters. A4, A3, Letter, Tabloid, and custom sizes. Print-ready: 300 DPI minimum for raster elements, vector for text and shapes. Bleed marks optional. CMYK color mode option. The poster layout engine respects a grid; no element overlaps another. Preview as PNG at 150 DPI.

7.3 Documents. Reports, proposals, contracts, letters. Real typographic hierarchy (title, subtitle, section, subsection, body, caption, footnote). Page numbers, table of contents (auto-generated from headings), bibliography (if research is cited).

7.4 The no-em-dash rule. This is a hard rule. The kernel's text output — PDFs, documents, agent messages, receipts, website copy — must never contain an em dash (—) or an en dash (–). Use a comma, semicolon, colon, parentheses, or a hyphen with spaces. Enforce at the kernel level: before any text is written to a PDF, document, or the console, scan for em/en dashes and either fix them or fail the write. Add a test.

7.5 The overlap rule. The layout engine for PDFs, posters, and documents computes bounding boxes. Two elements overlapping = build failure. Add a test that generates a poster with intentionally overlong text and asserts the layout engine pushes content to a second page rather than overlapping.

Acceptance: user types "make me a poster for a royal red product launch." Royal Red produces a print-ready A3 poster, verified visually, no overlap, no em dashes, with a 10/10 receipt.

9. Response quality — beat Claude, Codex, DeepSeek harness, and "buff code"
The user asked for Royal Red's responses to be "best from Claude, Codex, DeepSeek harness, and buff code."

9.1 Response protocol. Every agent response is now governed by a response protocol:

Lead with the answer. No preamble, no "Great question!"

No em dashes or en dashes. Ever. Kernel-enforced.

No emojis. Ever. Kernel-enforced.

No padding. If three words suffice, use three words. If a paragraph is needed, one paragraph, not five.

Structured when structure helps. Lists for parallel items, prose for narrative. Never a list where prose is clearer, never prose where a table is clearer.

Citations for facts. If the response contains a fact that came from a source, cite it with a link or a reference ID.

Honest about uncertainty. "I don't know" is a valid response. "I'm not sure, here's what I'd check" is a better response. Guessing is forbidden.

No marketing tone. No "powerful," "seamless," "revolutionary." Speak plainly.

9.2 Code quality. When Royal Red writes code:

Type-safe. TypeScript strict mode. Python type hints. No any, no unknown untyped.

Tested. Every function the agent writes gets at least one test unless the user explicitly says "no tests."

Documented. Every public function has a docstring. No noise comments (// increment i).

Named well. No data, info, temp, foo. Real names.

No copy-paste. If the same code appears twice, extract it.

Error handling. No bare try/catch that swallows. Errors are either handled or propagated.

No dead code. No commented-out blocks. No unused imports.

9.3 The "buff code" interpretation. The user said "buff code." Interpret this as: code that is strong, robust, tested, and defensively written. Not clever, not terse-for-the-sake-of-terseness. Code that a senior engineer would review without comments.

9.4 The comparison protocol. After every build, Royal Red produces a comparison receipt:

What Claude Code would have done (based on its known patterns)

What Codex CLI would have done

What DeepSeek harness would have done

What Royal Red did, and why it is better on the specific dimensions that matter: verification, honesty, completeness, no overlap, no em dashes, accessibility, performance

This is not marketing. It is a receipt. The user can audit it.

Acceptance: user asks Royal Red to "write a function that reverses a string in TypeScript." Royal Red produces: the function, a test, a docstring, no em dashes, no emojis, no padding, and a one-line note that this is trivial and no comparison is needed.
